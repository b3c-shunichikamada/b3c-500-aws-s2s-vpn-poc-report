§1 目的と全体像

AWS 東京リージョンに VPC を 2 つ作り、片方（VPC-A）を「疑似オンプレミス拠点」に見立てて VPN ルーターを置き、もう片方（VPC-B）の仮想プライベートゲートウェイ（VGW）と IPsec で結ぶ。各 VPC に確認用の EC2 を 1 台ずつ置き、VPN を通して双方向に Ping が通ることを確かめる。

通信の道筋（A から B へ Ping する場合）：EC2-A（10.10.1.10）→ 非公開ルート表で宛先 10.20.0.0/16 を vRX の LAN2 へ → vRX が IPsec で暗号化 → LAN1 から EIP 経由でインターネットへ → AWS の VPN エンドポイント → VGW → VPC-B のルート表 → EC2-B（10.20.1.10）。戻りは逆順（VPC-B のルート表で宛先 10.10.0.0/16 を VGW へ → AWS から vRX へ → vRX が復号して LAN2 から EC2-A へ）。

§2 VPC・サブネット・IP の設計

リージョンは ap-northeast-1。AZ は ap-northeast-1a の 1 つだけ（冗長化は対象外）。AZ は describe-instance-type-offerings で t3.medium と t3.micro の両方がある所から選んだ（実測：1a・1c・1d にあり、一覧の最初の 1a を採用）。既存の AWS リソースとの CIDR の重なりは 0 件（describe 系で確認済み、事前確認の記録）。

§3 vRX の 2 本の口と、既定の出口を LAN1 にした理由

2 本の口

口 ENI サブネット IP 役割
LAN1 ENI0（デバイス番号 0） 公開 10.10.0.0/24 10.10.0.10 + EIP インターネットへの口。IPsec のトンネルはここで張る
LAN2 ENI1（デバイス番号 1） 非公開 10.10.1.0/24 10.10.1.5 拠点内（EC2-A）側の口。VPN 宛ての通信はここへ届く

2 本の ENI とも、送信元／送信先チェック（自分宛てでない通信の転送を AWS が止める仕組み）を無効にした（SourceDestCheck=False、実測）。ルーターとして他の機器宛ての通信を中継するために必要。

既定の出口（デフォルトルート）を LAN1 にした理由

  • vRX の初期設定では、既定の出口が LAN2 になっている。
  • LAN2 側のサブネット（非公開）には、インターネットへ出る道（IGW へのルート）が無い。EIP を付けた ENI0（公開サブネット、デバイス番号 0）は LAN1 側にある。
  • 推測：既定の出口が LAN2 のままだと、インターネット宛て・AWS の VPN エンドポイント宛ての通信（IKE の UDP 500、NAT-T の UDP 4500）が LAN2 から出ようとして届かない。また、管理者 PC への SSH の戻りも、入ってきた口と別の口から出るため成立しない。 変更後に EIP の 22 番へ TCP が通ることを確認した（3 回とも True）。
  • 補足：Yamaha のガイドは「EIP を付ける ENI は LAN2（eth1）」と書いてあるが、本 PoC では公開サブネット側の ENI0 を LAN1 として EIP を付けた。ガイドと構成が違う点を、既定の出口を LAN1 に変えることで吸収できているかは、IPsec が UP になるまで未確認（試験結果は 05）。

VPN の暗号設定（Tunnel1。実測）

IKE バージョン＝ikev2／Phase1・Phase2 の暗号＝AES256／整合（ハッシュ）＝SHA2-256／Diffie-Hellman グループ＝14／DPD（死活確認）の動作＝restart／起動時の動作＝add（AWS 側からは張りに行かず、vRX から開始する）。Tunnel2 は AWS の既定値のまま、使わない。

セキュリティグループとネットワーク ACL

  • vrx-wan（vRX LAN1）：22/tcp は <ADMIN_IP>/32 のみ。500/udp と 4500/udp は、AWS の Tunnel1・Tunnel2 の外側 IP（13.196.38.153 ほか）の /32 だけ。0.0.0.0/0 の規則は 0 件（describe で確認済み）。
  • vrx-lan（vRX LAN2）：全プロトコルを 10.10.0.0/16 と 10.20.0.0/16 から許可。
  • ec2a・ec2b：ICMP を 10.0.0.0/8 から許可。22/tcp は対応する EIC Endpoint の SG からのみ許可。
  • eice-a・eice-b：受信の規則なし（送信は既定の全許可）。
  • ネットワーク ACL：両 VPC とも既定のまま（入出とも全許可）。

§6 当初の計画（Cisco C8000V）からの変更と理由

項目 当初の計画 実際 理由
VPN ルーター（SITE-A） Cisco Catalyst 8000V（Essentials PAYG を第一候補） Yamaha Virtual Router vRX（Rev.20.00.03、Marketplace、使用量ベース） Cisco の従量課金（PAYG）の製品（C8000V と ASAv の 2 製品）は、この AWS Japan のアカウントでは購読画面に「現在の地域ではご利用いただけません」と出て購読できなかった。vRX は購読できる画面を確認した
インスタンスタイプ t3.medium（Cisco） t3.medium（vRX） vRX のソフト代は t3.small でも t3.medium でも 0.02 USD/時で同じ。t3.medium なら今の IAM の許可で起動でき、付け直しが要らない（最短）
実接続の検証対象 Cisco Yamaha vRX Cisco と Fortinet は設定資料の作成（AWS の「Download configuration」で取れるサンプルの整理）だけ
送信元／送信先チェック Cisco で無効化 vRX の ENI 2 本で無効化 製品が変わっても必要な設定は同じ
管理アクセス Cisco は管理者 IP /32 からの SSH vRX も管理者 IP /32 からの SSH（22/tcp） 変更なし。初回ログインは EIC Endpoint 経由の SSH で行った
IAM v3 のポリシー v3 のポリシーに、AWS 管理ポリシー AmazonEC2FullAccess と EC2InstanceConnect を足した形 v3 では、ENI の属性変更と EIC Endpoint の作成で許可不足が出たため（ModifyNetworkInterfaceAttribute、EIC の ENI への CreateTags）。詳細は 02 の §0 と 06 の削除手順

変更しなかったもの：GOAL、2 つの VPC の CIDR、静的ルーティング、IKEv2、接続数 1、BGP・TGW・VPC Peering・NAT Gateway を使わない方針、冗長化なし。
